## Threat model

`/e2e/login` is enabled in production only as a release gate: setting `APAP_E2E_AUTH_ENABLED=true` registers a route that mints a valid session for `APAP_E2E_AUTH_DEFAULT_EMAIL` when a caller presents the shared secret in `X-E2E-Secret`. An attacker who obtains the secret obtains a full session; an attacker who does not can still probe the endpoint. The layered posture is:

1. **Secret as primary gate.** The route requires an exact, constant-time match (`hmac.compare_digest` over UTF-8 bytes behind an ASCII guard) against `APAP_E2E_AUTH_SECRET`; a missing, wrong, or non-ASCII header answers `401` before any session is written. The ASCII guard matters because ASGI decodes header bytes with latin-1, so a raw non-ASCII probe byte (e.g. `0xE9`) reaches the handler as a non-ASCII `str`, which made `hmac.compare_digest` raise `TypeError` — an unhandled 500 with no audit entry — before fix round 1 (`377c902`). Non-ASCII probes can never match the expected secret, so denying them without a byte comparison is behaviourally identical and now audit-covered.
2. **Rate limit as backstop.** A per-IP sliding-window bucket (5 attempts/minute) bounds online guessing of the secret and turns brute-force into a logged, throttled, and observable activity. The secret remains the actual authentication decision; the bucket never grants access.
3. **Audit for forensics.** Every attempt emits one structured `e2e.login` entry (outcome, capped target email, origin IP) on **every** branch — `ok`, `invalid_secret`, `invalid_request` (the 400 empty-target-email branch), `server_misconfigured` (the 503 empty-configured-secret branch), and `rate_limited` (emitted by the rate-limit middleware when the bucket denies) — so that probing, credential-stuffing attempts against the gate, and legitimate release-gate usage are distinguishable from stdout logs after the fact. The raw `?email=` query param is truncated to 120 characters before it reaches `log_safe`.

## Controls verified

1. **C1 — Audit event on every attempt and every branch (AC1, `836c3bc`, `377c902`).** All four handler branches emit `log_safe("e2e.login", outcome=…, target_email=…, client_ip=…)`: the rejected-secret path (`invalid_secret`), the success path (`ok`), the 400 empty-target-email branch (`invalid_request`), and the 503 empty-configured-secret branch (`server_misconfigured`). Non-ASCII secret probes land on the `invalid_secret` branch instead of crashing. Verified by `tests/test_e2e_auth.py::test_audit_log_emitted_on_success`, `::test_audit_log_emitted_on_invalid_secret`, `::test_audit_log_emitted_on_empty_email_400`, `::test_audit_log_emitted_on_misconfigured_503`, and `::test_non_ascii_secret_header_lands_on_invalid_secret_with_audit`. The tests assert the raw secret never appears in the record and that the recorded email is capped at 120 characters (`::test_audit_target_email_is_capped`).
2. **C2 — Rate limit 5/min/IP with 429, only when the route is registered (AC2, `23d7cce`, `8564841`).** `RateLimitMiddleware._handle_e2e_login` hits the `e2e_login` scope of the shared `InProcessRateLimitBackend` sliding window — and the middleware applies the bucket only when `Settings.e2e_auth_enabled` is True (the route actually registered). With the flag off, `GET /e2e/login` answers the same bare 404 as any unknown path: no `X-RateLimit-*` headers, no bucket consumption. The 6th flag-on request from the same IP within 60 seconds gets the shared 429 shape (`Retry-After` + `X-RateLimit-*` headers), a `log_safe("ratelimit.rejected", scope="e2e_login", …)` entry with no IP kwarg (REQ-5/D6), **and** one additional IP-bearing forensic `e2e.login` entry (`outcome=rate_limited`, `client_ip`, capped raw email) so brute-force bursts stay attributable. Verified by `TestE2ELoginRateLimit` in `tests/test_rate_limit_middleware.py`, including per-IP bucket isolation, the flag-off bare-404 sequence, the forensic-record cardinality, and the e2e-only scope of the forensic event (`::test_oauth_429_does_not_emit_forensic_record`). AC2 is **per-worker**: the bucket is worker-local in-process state, exact under the current single Coolify worker.
3. **C3 — Flag-off 404 pinned at composition level (AC3, `6c99f9f`, `377c902`).** Against the real `create_app`: with `APAP_E2E_AUTH_ENABLED` forced off the app answers `404`; with the flag and secret set the route exists and answers `401` without the header (positive control). Verified by `test_production_app_answers_404_when_flag_absent` and `test_production_app_registers_route_when_flag_enabled` in `tests/test_e2e_auth.py`. Both composition tests force the setting through an explicit env-var value (`monkeypatch.setenv`) because `Settings` reads `env_file='.env'` and `monkeypatch.delenv` cannot clear a developer-local `.env` entry — the delenv form flipped the 404 test red spuriously on machines with a local `.env` (dual-review finding A-006).
4. **C4 — Bucket key ignores untrusted X-Forwarded-For (disposition pin, `8564841`).** With `APAP_TRUST_XFF` unset/false (the default; no manifest sets it true), a client-supplied multi-hop `X-Forwarded-For` cannot reset the bucket key: `_extract_identity` ignores X-Forwarded-For when trust is off, so rotating the leftmost entry does not buy a fresh 5-attempt budget. Pinned by `TestE2ELoginRateLimit::test_bucket_key_ignores_client_supplied_xff_when_untrusted`. No X-Forwarded-For redesign happened in this fix round; it is tracked in a follow-up issue.

## Design decisions

1. **Audit field names sit outside the closed redaction list.** The issue mandates recording the requested email and origin IP, but `email` and `ip_address` are two of the twelve fields redacted by `log_safe`. Rather than weakening the closed list, the events use the semantically distinct names `target_email` and `client_ip`. This policy is documented cross-ref in `docs/codebase/logging-conventions.md` ("Eventos de auditoría con PII exigida por un issue", added in `836c3bc`): the closed list does not change, and extending it remains a deliberate, reviewed change. The secret value is never a field of the event.
2. **Rate-limit state is worker-local in-process; AC2 is per-worker.** The bucket lives in the in-process backend installed by `install_rate_limit_middleware` — the same state scope as the auth cache per §29/#262. This means AC2's 5/min/IP ceiling is enforced **per worker**: with the current single Coolify worker this is exact; if workers or replicas are ever added, each worker enforces its own 5/min and the effective global ceiling multiplies accordingly. The same TTL-0 / multi-worker review as `docs/runbooks/auth-cache-multi-worker.md` applies before scaling. As a backstop that never grants access, per-worker state is an acceptable precision trade for zero shared-infrastructure dependency.
3. **Flag-off probes get a bare 404 with no rate-limit state.** The middleware applies the `e2e_login` bucket only when the route is actually registered (`Settings.e2e_auth_enabled` True). With the flag off, `GET /e2e/login` answers the same bare 404 as any unknown path — no `X-RateLimit-*` headers and no bucket consumption. This reverses the earlier deliberate-design note that 404 probes consume bucket state: dual review (dual-review findings B-001/A-003) showed the limiter was fingerprinting the disabled endpoint (the 404 carried rate-limit headers and the 6th probe returned 429, distinguishing a disabled `/e2e/login` from any other unknown path). The enumeration-protection goal is still served: the bare 404 gives an attacker nothing to distinguish the path, and once the gate is enabled the bucket bounds probe volume exactly as before.
4. **Rejection logging is two-tiered.** `ratelimit.rejected` keeps its shared, IP-free shape for every scope (REQ-5, D6). For the `e2e_login` scope only, the 429 additionally emits one IP-bearing `e2e.login` forensic event (`outcome=rate_limited`, `client_ip`, capped raw email) because brute-force bursts against the gate would otherwise lose the source IP and the attempted email from the forensic trail (dual-review finding B-003). Other scopes (oauth, write) do not emit the forensic event — pinned by test.
5. **Ceiling is a module constant, not a `Settings` field.** `E2E_LOGIN_RATE_LIMIT_PER_MIN = 5` keeps the guard autonomous from configuration: the limit cannot be relaxed per-environment without a code change, which matches its role as an unconfigurable backstop. The shared secret remains the primary gate and is the only knob intended for operators.
6. **Secret rotation is an operator runbook, not this audit.** Rotation of `APAP_E2E_AUTH_SECRET` is tracked as the runbook sub-issue #907 (see #905). This audit records the pointer; the runbook will own trigger conditions, the rotation procedure, and rollback.

## Verdict

**PASS for the audited scope after fix round 1.** The E2E login surface now fails closed (flag off → bare 404, identical to any unknown path, pinned at composition level and free of rate-limit fingerprints), fails slow (5/min/IP backstop with the shared 429 shape, applied only when the route is registered, per-worker as documented), and leaves one structured `log_safe` entry per attempt on every branch — including 400/503, rate-limited probes with an IP-bearing forensic event, and non-ASCII secret probes that previously crashed with an unhandled 500 — with the secret as the sole authentication decision and never a log field, and the recorded email capped at 120 characters.

## Residual risks and future hardening

- **X-Forwarded-For trust is the identity boundary; a trusted misconfiguration lets clients rotate identity.** With `trust_xff=false` (the default; no manifest sets it true), `X-Forwarded-For` is ignored entirely for both the bucket key and the audit IP — a client-supplied leftmost entry cannot reset the bucket or forge the audit IP (pinned by test). With `trust_xff=true`, however, a client-supplied leftmost entry can rotate both the bucket key and the audit IP, buying fresh 5-attempt budgets and polluting the forensic trail. This is an accepted residual risk under the assumed proxy topology (the Coolify reverse proxy is the only ingress and overwrites X-Forwarded-For); it requires an operator to set `APAP_TRUST_XFF=true` against that assumption. The X-Forwarded-For handling redesign (rightmost-trusted-hop resolution) is tracked in a follow-up issue and was deliberately out of scope for of this fix round.
- **Worker-local state resets on deploy/restart.** A restart clears bucket state, so a window boundary grants a brief extra allowance. Accepted: the secret, not the bucket, is the gate. AC2 is per-worker; see Design decision 2.
- **Shared egress IPs.** Several legitimate clients behind the same shared egress address share a bucket and can exhaust the 5/min ceiling. Accepted for a release-gate tool that is not user-facing.
- **No IP allowlist.** An allowlist restricting `/e2e/login` to known runner IPs is recorded as optional future hardening; the rate limit and the secret were chosen as the #904 scope.
- **Rotation runbook pending.** Secret rotation currently relies on the sub-issue #907 runbook (#905) landing before the gate is used for a real release cycle.
